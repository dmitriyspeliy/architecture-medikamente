# Отчёт по узким местам при миграции

## 1. Цель

Цель миграции — перейти от файлового и ручного ландшафта к целевой цифровой архитектуре, которая поддерживает:

- пятикратный рост объёма данных;
- открытие новых филиалов;
- клиентский портал и мобильное приложение;
- централизованный учёт пациентов, записей, медицинских документов и оплат;
- безопасные интеграции с лабораторией, платёжными системами и 1С;
- аналитическую платформу для BI, ML и AI.

Основной риск миграции:

```text
Снижение производительности и устойчивости системы
во время и после перехода на новую архитектуру
```

---

## 2. Текущее состояние

Существующая система состоит из:

- Excel-файлов с пациентами, журналами записей, оплатами и лабораторными реестрами;
- PDF- и JPG-документов на общем файловом сервере;
- файловых баз «1С:Бухгалтерия предприятия» и «1С:Торговля и склад»;
- Exchange Mail Server;
- Active Directory;
- ККМ, связанной с 1С через TCP/IP и OLE;
- одного физического сервера Windows Server 2022;
- ручных операций без полного аудита и централизованного контроля потоков данных.

Текущий ландшафт не является классическим программным монолитом, но фактически представляет собой монолитный инфраструктурный и операционный контур:

- один сервер;
- общий файловый ресурс;
- тесно связанные процессы;
- отсутствие разделения доменов;
- сильная зависимость от ручной работы;
- отсутствие единых контрактов и источников истины.

## 4. Категории потенциальных узких мест

## 4.1. Данные

### Проблемы

1. **Низкое качество исходных данных**

   Excel-файлы могут содержать:

   - дубликаты пациентов;
   - различные форматы Ф. И. О., телефонов и дат;
   - пустые обязательные поля;
   - несовместимые идентификаторы;
   - ошибки ручного ввода;
   - несколько актуальных версий одного файла.

2. **Отсутствие единого идентификатора пациента**

   Один пациент может быть представлен по-разному:

   ```text
   Иванов Иван Иванович
   Иванов И. И.
   ИВАНОВ ИВАН
   ```

   Без master data management миграция создаст дубли и неверные связи между приёмами, анализами, оплатами и документами.

3. **Большой объём неструктурированных данных**

   PDF, JPG и сканы:

   - требуют отдельной миграции;
   - создают нагрузку на storage и сеть;
   - сложно проверяются автоматически;
   - могут не иметь корректной связи с пациентом.

4. **Неопределённая актуальность данных**

   Неизвестно:

   - какой Excel-файл является источником истины;
   - какие документы устарели;
   - какие данные можно удалить;
   - какие данные обязательны к переносу.

5. **Рост индексов и тяжёлые запросы**

   После миграции в централизованные БД возможны:

   - неоптимальные запросы;
   - full scan;
   - блокировки;
   - большие join;
   - рост таблиц аудита;
   - деградация при построении отчётов на production-БД.

### Последствия

- увеличение времени миграции;
- ошибки связывания данных;
- потеря документов;
- медленные запросы;
- неверные медицинские и финансовые данные;
- остановка бизнес-процессов при cutover.

## 4.2. Архитектура и программное обеспечение

### Проблемы

1. **Ошибочная декомпозиция на микросервисы**

   Раннее дробление на большое число сервисов может привести к:

   - chatty communication;
   - множеству сетевых вызовов;
   - сложным распределённым транзакциям;
   - высокой операционной стоимости;
   - усложнению отладки.

2. **Синхронные цепочки вызовов**

   Пример потенциально опасного потока:

   ```text
   Client Portal
       → Appointment Service
       → Patient Service
       → Doctor Service
       → Notification Service
       → Audit Service
   ```

   Отказ или задержка одного компонента увеличивает latency всей операции.

3. **Распределённые транзакции**

   Процессы оплаты, записи, лабораторных назначений и бухгалтерского учёта требуют согласованности между несколькими системами.

   Использование двухфазного commit между сервисами будет слабым решением из-за:

   - блокировок;
   - сложного восстановления;
   - зависимости от доступности всех участников.

4. **Недостаточная идемпотентность**

   Повторные запросы могут привести к:

   - двойной записи пациента;
   - повторному списанию оплаты;
   - повторной фискализации;
   - дублированию лабораторного заказа;
   - повторной проводке в 1С.

5. **Отсутствие backpressure**

   При пиковых нагрузках notification, integration и analytics-конвейеры могут накапливать очередь и создавать дополнительную нагрузку на core-сервисы.

6. **Неправильная стратегия кэширования**

   Кэш может:

   - содержать устаревшее расписание;
   - возвращать отменённые слоты;
   - раскрывать данные не тому пользователю;
   - создавать неконсистентность между филиалами.

### Последствия

- рост latency;
- cascading failure;
- сложные инциденты;
- потеря согласованности;
- увеличение стоимости сопровождения.

---

## 4.3. Инфраструктура

### Проблемы

1. **Один физический сервер**

   Текущий сервер является единой точкой отказа для:

   - AD;
   - DNS;
   - DHCP;
   - файлов;
   - Exchange;
   - 1С;
   - ККМ-интеграции.

2. **Недостаточная пропускная способность сети**

   Открытие филиалов увеличит:

   - WAN-трафик;
   - передачу медицинских документов;
   - число API-вызовов;
   - объём синхронизации;
   - нагрузку на VPN.

3. **Storage bottleneck**

   Медицинские файлы и резервные копии могут создать:

   - высокую нагрузку на IOPS;
   - конкуренцию БД и object storage;
   - медленное восстановление;
   - рост времени backup.

4. **Неправильная конфигурация Kubernetes**

   Возможные проблемы:

   - недостаточные resource requests/limits;
   - отсутствие HPA;
   - неверные readiness/liveness probes;
   - слишком маленькие connection pools;
   - отсутствие pod anti-affinity;
   - хранение stateful workload без подходящего storage.

5. **Ограничения базы данных**

   Одна PostgreSQL-инсталляция без:

   - read replicas;
   - connection pooler;
   - partitioning;
   - monitoring;
   - slow query analysis

   станет центральным bottleneck.

6. **Недостаточная резервная инфраструктура**

   Без отдельного DR-контура миграция увеличивает риск длительного простоя.

### Последствия

- недоступность всех сервисов;
- медленная работа филиалов;
- деградация БД;
- невозможность быстро восстановить систему.

---

## 4.4. Интеграции

### Проблемы

1. **Файловая 1С и OLE**

   Файловая база и OLE плохо подходят для высоконагруженного и распределённого доступа.

   Возможны:

   - блокировки файловой базы;
   - медленный обмен;
   - ошибки при параллельной обработке;
   - зависимость от Windows-сервера;
   - отсутствие стабильных API-контрактов.

2. **Лаборатория**

   Риски:

   - нестабильный внешний API;
   - длительное время ответа;
   - различия схем данных;
   - дубли результатов;
   - некорректная привязка результата к пациенту.

3. **Платёжный провайдер и ККМ**

   Возможны:

   - таймаут после успешной оплаты;
   - повторный callback;
   - рассинхронизация оплаты и чека;
   - недоступность ОФД;
   - ручная сверка.

4. **Уведомления**

   Массовые напоминания за день до приёма могут создать:

   - spike нагрузки;
   - очередь отправки;
   - throttling внешнего провайдера;
   - повторные сообщения.

5. **Связь с аналитической платформой**

   Прямое чтение production-БД аналитикой приведёт к конкуренции за CPU, I/O и connections.

### Последствия

- зависшие бизнес-процессы;
- повторные операции;
- несогласованные статусы;
- деградация core-систем.

---

## 4.5. Процессы миграции

### Проблемы

1. **Big Bang migration**

   Одновременное отключение Excel, файловых систем и 1С-интеграций создаёт критический риск полной остановки бизнеса.

2. **Dual-write**

   Параллельная запись в старую и новую системы может привести к рассинхронизации.

   Пример:

   ```text
   Новая система: запись создана
   Excel: обновление не выполнено
   ```

3. **Отсутствие rollback**

   Если cutover выполнен без обратимого сценария, восстановление потребует ручной работы.

4. **Недостаточная проверка данных**

   Проверка только количества строк не выявит:

   - неверные связи;
   - неправильные документы;
   - потерянные согласия;
   - расхождения сумм;
   - некорректные статусы.

5. **Недостаточное нагрузочное тестирование**

   Проверка только среднего трафика не покрывает:

   - утренний пик записи;
   - массовые уведомления;
   - закрытие бухгалтерского периода;
   - загрузку лабораторных результатов;
   - массовую миграцию документов.

6. **Параллельная миграция всех доменов**

   Одновременная миграция пациентов, медицинских карт, платежей, HR и склада создаст слишком широкий blast radius.

### Последствия

- остановка процессов;
- потеря данных;
- длительный rollback;
- скрытые ошибки после запуска.

---

## 4.6. Персонал и эксплуатация

### Проблемы

1. **Недостаток компетенций**

   Текущая IT-команда состоит из трёх человек, при этом целевая архитектура требует знаний:

   - Kubernetes;
   - PostgreSQL;
   - Kafka;
   - observability;
   - security;
   - CI/CD;
   - data engineering;
   - SRE.

2. **Непривычные процессы пользователей**

   Ресепшен, врачи, кассиры и бухгалтерия привыкли к Excel и 1С.

   Возможны:

   - ошибки при работе с новым интерфейсом;
   - обход системы;
   - ведение теневых Excel-файлов;
   - увеличение времени операций.

3. **Отсутствие эксплуатационных регламентов**

   Не определены:

   - SLO и SLA;
   - on-call;
   - incident response;
   - RTO и RPO;
   - порядок rollback;
   - ответственность за интеграции.

4. **Недостаточная observability**

   Без сквозных метрик и трассировки команда не сможет определить, где возникает bottleneck.

### Последствия

- медленное устранение инцидентов;
- рост ручной работы;
- возврат к Excel;
- нестабильная эксплуатация.

## 5. Диаграмма Исикавы

Центральная проблема диаграммы:

```text
Снижение производительности и устойчивости
во время и после миграции
```

Основные ветви:

| Категория | Основные причины |
|---|---|
| Данные | Дубли, плохое качество, неструктурированные файлы, отсутствие master ID |
| Архитектура и ПО | Chatty API, распределённые транзакции, отсутствие идемпотентности |
| Инфраструктура | Один сервер, слабая сеть, storage IOPS, ограничения БД |
| Интеграции | Файловая 1С, OLE, таймауты лаборатории, повторные callbacks |
| Процессы миграции | Big Bang, dual-write, отсутствие rollback и reconciliation |
| Персонал и эксплуатация | Нехватка компетенций, отсутствие SLO и observability |

## 6. Рекомендации

## 6.1. Приоритет P0 — до начала production-миграции

| Мера | Причина |
|---|---|
| Провести профилирование и очистку данных | Иначе миграция перенесёт ошибки и дубли |
| Ввести единый `patient_id` и правила дедупликации | Критично для связи записей, карт, анализов и оплат |
| Отказаться от Big Bang | Снижает blast radius |
| Подготовить rollback и reconciliation | Без них невозможно безопасно переключиться |
| Реализовать идемпотентность критичных операций | Исключает двойные оплаты, записи и проводки |
| Провести нагрузочное тестирование критичных сценариев | Позволяет выявить bottleneck до запуска |
| Вынести аналитические нагрузки из production-БД | Предотвращает деградацию операционных сервисов |
| Настроить базовую observability | Без метрик невозможно управлять миграцией |

## 6.2. Приоритет P1 — первый этап миграции

| Мера | Причина |
|---|---|
| Применить Strangler Fig Pattern | Позволяет мигрировать домены постепенно |
| Начать с Patient Registry и Appointment Service | Они формируют основу MVP |
| Использовать transactional outbox | Снижает риск рассинхронизации |
| Добавить connection pooler и slow query monitoring | Защищает PostgreSQL от connection bottleneck |
| Ввести API Gateway и timeouts/retries/circuit breaker | Ограничивает cascading failure |
| Перевести документы в object storage | Снижает нагрузку на файловый сервер |
| Изолировать интеграции с 1С адаптером | Ограничивает влияние legacy-системы |
| Ввести очереди для уведомлений и внешних интеграций | Сглаживает пики нагрузки |

## 6.3. Приоритет P2 — после стабилизации MVP

| Мера | Причина |
|---|---|
| Декомпозировать оставшиеся домены | После получения эксплуатационных данных |
| Добавить read replicas и partitioning | При подтверждённом росте нагрузки |
| Внедрить полноценный DR-контур | Для отказоустойчивости филиальной системы |
| Развить Data Platform | После стабилизации источников данных |
| Внедрить autoscaling по бизнес-метрикам | После накопления профиля нагрузки |

## 7. Рекомендуемая стратегия миграции

### Этап 1. Подготовка

- инвентаризация источников;
- data profiling;
- классификация данных;
- определение владельцев;
- формирование canonical data model;
- введение `patient_id`;
- подготовка observability;
- baseline производительности текущей системы.

### Этап 2. MVP

Первым мигрируется контур:

```text
Patient Registry
    +
Appointment Service
    +
Employee Portal
    +
Client Portal
```

Excel остаётся только временным read-only источником или архивом.

### Этап 3. Медицинский контур

- электронная медицинская карта;
- миграция файлов;
- связь документов с пациентом;
- интеграция с лабораторией;
- аудит доступа.

### Этап 4. Платежи и 1С

- Payment Service;
- ККМ/ОФД;
- integration adapter;
- reconciliation;
- постепенное отключение двойного Excel-учёта.

### Этап 5. Аналитика

- CDC или event-based ingestion;
- Data Lake;
- Protected Zone;
- Trusted Analytics Zone;
- BI/ML/AI.

### Этап 6. Вывод legacy

Legacy-компонент отключается только после:

- проверки полноты данных;
- reconciliation;
- завершения периода параллельного чтения;
- успешного rollback rehearsal;
- подтверждения владельца бизнес-процесса.

## 8. Архитектурные механизмы снижения bottleneck

### Для API

- timeouts;
- retry только для безопасных операций;
- exponential backoff;
- circuit breaker;
- bulkhead;
- rate limiting;
- request size limits.

### Для БД

- индексирование по фактическим запросам;
- connection pooling;
- pagination;
- partitioning больших таблиц;
- архивирование audit-данных;
- read replicas для отчётов;
- запрет N+1;
- slow query log.

### Для Kafka и очередей

- partition key по `patient_id` или aggregate ID;
- идемпотентный consumer;
- retry topic;
- dead-letter topic;
- monitoring consumer lag;
- backpressure;
- контроль размера сообщений;
- хранение файлов вне Kafka.

### Для документов

- object storage;
- асинхронная обработка;
- checksum;
- virus scan;
- pre-signed URL;
- lifecycle policy;
- CDN только для разрешённого контента.

### Для Kubernetes

- resource requests и limits;
- HPA;
- PodDisruptionBudget;
- anti-affinity;
- readiness/liveness/startup probes;
- graceful shutdown;
- rolling update;
- отдельные node pools для stateful и stateless workloads.

## 9. Метрики контроля

| Область | Метрики |
|---|---|
| API | p50/p95/p99 latency, RPS, error rate |
| БД | query latency, locks, connections, cache hit ratio |
| Kafka | consumer lag, retry rate, DLQ volume |
| Storage | IOPS, throughput, latency, capacity |
| Интеграции | timeout rate, retry rate, duplicate rate |

| Документы | migrated files, checksum failures, orphan files |
| Пользователи | operation time, failed actions, shadow Excel usage |
| Инфраструктура | CPU, memory, pod restarts, node pressure |

## 10. Критерии готовности к cutover

Cutover допускается, если:

- мигрировано и сверено 100% критичных сущностей;
- отсутствуют неразрешённые дубли пациентов;
- критичные операции идемпотентны;
- rollback проверен на тестовом прогоне;
- p95 latency соответствует целевому SLO;
- error rate не превышает установленный порог;
- backup и restore проверены;
- интеграции с лабораторией, платёжным провайдером и 1С прошли fault testing;
- SIEM и observability получают необходимые события;
- бизнес-владельцы подтвердили корректность данных.

## 11. Вывод

Главные bottleneck миграции находятся не только в производительности отдельных сервисов.

Критические риски связаны с:

- качеством и связностью исходных данных;
- файловой 1С и OLE;
- отсутствием идемпотентности;
- неправильной декомпозицией;
- попыткой выполнить Big Bang;
- ограничениями текущей инфраструктуры;
- нехваткой эксплуатационных процессов.

Рекомендуемый подход — поэтапная миграция по Strangler Fig Pattern с обязательными reconciliation, rollback, observability и нагрузочным тестированием.
