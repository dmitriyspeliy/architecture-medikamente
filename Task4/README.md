# Задание 4. Оценка узких мест при миграции

## Цель

Выявить потенциальные узкие места, которые могут снизить производительность и устойчивость системы во время и после миграции с текущего файлового и монолитного контура на современную архитектуру.

## Состав решения

- `migration-bottlenecks-report.md` — подробный анализ текущего состояния, рисков, последствий и мер снижения узких мест.
- `diagrams/ishikawa-migration-bottlenecks.drawio` — редактируемая диаграмма Исикавы.
- `diagrams/ishikawa-migration-bottlenecks.png` — изображение диаграммы для быстрого просмотра.

## Центральная проблема

```text
Снижение производительности и устойчивости системы
во время и после миграции
```

## Основные категории причин

1. Данные.
2. Архитектура и программное обеспечение.
3. Инфраструктура.
4. Интеграции.
5. Процессы миграции.
6. Персонал и эксплуатация.

## Ключевые риски

- низкое качество Excel-данных;
- отсутствие единого идентификатора пациента;
- большой объём PDF/JPG и других неструктурированных документов;
- ошибочная декомпозиция на микросервисы;
- синхронные цепочки вызовов;
- распределённые транзакции;
- отсутствие идемпотентности;
- зависимость от файловой 1С и OLE;
- один физический сервер;
- ограничения сети, storage и PostgreSQL;
- Big Bang cutover;
- dual-write и рассинхронизация;
- отсутствие rollback и reconciliation;
- недостаточное нагрузочное тестирование;
- нехватка компетенций и observability.

## Приоритетные меры

### P0

- провести data profiling и очистку данных;
- ввести единый `patient_id`;
- отказаться от Big Bang;
- подготовить rollback и reconciliation;
- реализовать идемпотентность критичных операций;
- провести нагрузочное и fault-тестирование;
- вынести аналитику из production-БД;
- настроить базовую observability.

### P1

- использовать Strangler Fig Pattern;
- начать с Patient Registry и Appointment Service;
- внедрить transactional outbox;
- изолировать 1С через integration adapter;
- использовать очереди для уведомлений и внешних интеграций;
- добавить connection pooling и slow query monitoring.

### P2

- развивать декомпозицию после стабилизации MVP;
- добавить read replicas и partitioning при подтверждённой нагрузке;
- внедрить DR-контур;
- развивать Data Platform;
- настроить autoscaling по фактическим метрикам.

## Рекомендуемая стратегия миграции

```text
Подготовка данных
    ↓
Patient Registry + Appointment Service
    ↓
Медицинский контур
    ↓
Платежи и 1С
    ↓
Аналитическая платформа
    ↓
Вывод legacy
```

Каждый этап должен завершаться:

- reconciliation;
- проверкой производительности;
- проверкой rollback;
- подтверждением бизнес-владельца;
- контролем технических и бизнес-метрик.
