# Cutover-план миграции на новую платформу

## 1. Выбранная стратегия

Для компании «Медикаменте» выбрана стратегия **Parallel run**.

Старый и новый контуры временно работают параллельно. На каждом этапе определяется единый источник истины для конкретного домена, выполняется сверка данных и только после подтверждения корректности нагрузка окончательно переводится на новую платформу.

Целевая последовательность:

```text
Legacy — основной источник
        ↓
Новая система — shadow/read-only
        ↓
Параллельная работа и reconciliation
        ↓
Новая система — основной источник
        ↓
Legacy — read-only
        ↓
Вывод legacy
```

## 2. Обоснование выбора

### Почему выбран Parallel run

Текущий контур включает:

- Excel-файлы;
- общий файловый сервер;
- файловые базы 1С;
- ручные операции;
- ККМ через TCP/IP и OLE;
- обмен с лабораторией и внешними системами;
- медицинские, платёжные и кадровые данные.

Полное одномоментное переключение создаёт неприемлемый риск:

- потери записей на приём;
- неверной привязки медицинских документов;
- расхождения оплат и чеков;
- потери данных в 1С;
- остановки работы филиала;
- невозможности быстро восстановить исходное состояние.

### Почему не High-level design

High-level design необходим как архитектурная практика, но сам по себе не задаёт безопасный порядок переключения production-нагрузки и не решает вопрос сверки данных между старым и новым контурами.

### Почему не Branch by abstraction

Branch by abstraction эффективен, когда существует программный монолит с изменяемыми внутренними интерфейсами. В текущем ландшафте значительная часть процессов реализована через Excel, файлы, 1С и ручные действия. Встроить единый абстрактный слой во все эти компоненты без существенной переработки невозможно.

### Преимущества Parallel run

- сохранение непрерывности работы;
- сравнение результатов старой и новой систем;
- постепенный перевод по доменам;
- возможность отката;
- снижение blast radius;
- подтверждение корректности на реальных данных.

### Ограничения Parallel run

- временное увеличение операционной сложности;
- необходимость reconciliation;
- риск двойной работы сотрудников;
- риск рассинхронизации;
- повышенная нагрузка на поддержку;
- необходимость жёстко определить источник истины на каждом этапе.

## 3. Принципы cutover

1. Для каждого домена в каждый момент времени определён один master/source of truth.
2. Двусторонний dual-write не используется как постоянный механизм.
3. Все критичные операции должны быть идемпотентными.
4. Каждое переключение выполняется по отдельному домену.
5. Переход на следующий этап допускается только после выполнения exit criteria.
6. Для каждого этапа заранее определён rollback.
7. Legacy после cutover переводится в read-only.
8. Удаление legacy выполняется только после завершения периода стабилизации и архивирования.

## 7. Go/No-Go checklist

### Технические условия

- production backup создан и проверен;
- rollback протестирован;
- все миграционные скрипты versioned;
- нет критичных дефектов;
- p95/p99 соответствуют SLO;
- monitoring и alerting работают;
- SIEM получает события;
- внешние интеграции доступны;
- capacity reserve не менее 30%;
- deployment artifacts зафиксированы.

### Данные

- сверено 100% критичных сущностей;
- количество записей совпадает;
- financial totals совпадают;
- нет неразрешённых дублей;
- документы имеют checksum;
- нет orphan records;
- delta migration завершена;
- error queue пуста либо одобрена.

### Бизнес

- бизнес-владельцы подтвердили корректность;
- пользователи обучены;
- support готов;
- инструкции rollback распространены;
- окно миграции согласовано;
- внешние партнёры уведомлены.

### Решение

```text
GO:
все blocker-критерии выполнены.

NO-GO:
есть хотя бы один P0 blocker,
rollback не подтверждён,
нет backup,
не выполнена сверка финансовых или медицинских данных.
```

## 8. План отката

## 8.1. Условия немедленного rollback

Rollback запускается, если:

- недоступны критичные функции более 15 минут;
- превышен error rate;
- обнаружена потеря или повреждение данных;
- появились двойные оплаты;
- возникли массовые конфликты записей;
- не формируются чеки;
- недоступны медицинские документы;
- не работает авторизация критичных ролей;
- нарушены требования безопасности;
- p95 latency превышает допустимый порог в течение установленного времени.

## 8.2. Последовательность rollback

1. Cutover Manager объявляет rollback.
2. Останавливается входящий write-трафик в новую систему.
3. Фиксируется журнал операций после T0.
4. Routing возвращается на legacy.
5. Legacy переводится в write-mode.
6. Операции новой системы помещаются в reconciliation queue.
7. Проверяется целостность legacy.
8. Пользователи уведомляются.
9. Выполняется разбор расхождений.
10. Назначается новый cutover только после RCA.

## 8.3. Типы отката

| Тип | Когда применяется |
|---|---|
| Traffic rollback | Новая система технически нестабильна, данные не повреждены |
| Domain rollback | Ошибка ограничена одним доменом |
| Data rollback | Повреждены или неверно мигрированы данные |
| Integration rollback | Не работает одна внешняя интеграция |
| Full rollback | Нарушены несколько критичных процессов |

### Технические метрики

- API p50/p95/p99;
- error rate;
- CPU и memory;
- database connections;
- lock wait;

- Kafka consumer lag;

## 12. Exit criteria

Миграция считается завершённой, если:

- новая платформа работает в соответствии с SLO;
- нет критичных дефектов;
- данные сверены;
- legacy не используется для новых операций;
- все критичные интеграции стабильны;
- backup и restore подтверждены;
- support работает по новым регламентам;
- hypercare завершён;
- бизнес-владельцы подписали acceptance;
- legacy архивирован и подготовлен к выводу.

## 13. Итог

Parallel run выбран как наиболее безопасная стратегия для медицинской компании с файловым legacy-контуром, ручными процессами и критичными медицинскими и финансовыми данными.

Ключевые условия успеха:
