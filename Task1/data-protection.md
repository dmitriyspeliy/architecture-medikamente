# Категории данных и способы защиты

## 1. Цель документа

Документ определяет категории конфиденциальных данных компании «Медикаменте» и меры защиты, которые должны применяться при сборе, передаче, обработке, хранении, аналитическом использовании и удалении данных.

## 2. Уровни конфиденциальности

| Уровень | Описание | Примеры |
|---|---|---|
| `PUBLIC` | Информация, предназначенная для открытого распространения | Адрес филиала, перечень услуг |
| `INTERNAL` | Внутренняя информация компании | Инструкции, внутренние справочники |
| `CONFIDENTIAL` | Персональные, договорные, финансовые и кадровые данные | Контакты, платежи, договоры |
| `RESTRICTED` | Медицинские данные и данные, раскрытие которых создаёт критический риск | Диагнозы, результаты анализов, медицинские карты |

## 3. Методы защиты

### 3.1. Шифрование

Применяется для обеспечения конфиденциальности данных:

- при хранении — шифрование дисков, баз данных, файлов и резервных копий;
- при передаче — TLS 1.2 или TLS 1.3;
- на уровне отдельных полей — для наиболее чувствительных атрибутов.

Ключи шифрования должны храниться отдельно от данных в системе управления ключами.

### 3.2. Маскирование и обфускация

Используются для сокрытия части значения в интерфейсах, отчётах и журналах.

Примеры:

```text
Телефон: +7 *** ***-12-34
Email: d***@example.ru
Ф. И. О.: Ива*** Иван Ива***
```

Маскирование не является самостоятельной криптографической защитой и должно применяться совместно с контролем доступа и шифрованием.

### 3.3. Псевдонимизация

Идентификаторы пациента заменяются техническими токенами.

Пример:

```text
patient_id: 7d8b11e2-81cd-4ae0-85af-ff4ab682f816
```

Таблица соответствия между токеном и пациентом хранится отдельно и доступна только ограниченному числу сервисов.

Псевдонимизация используется:

- при обмене с лабораторией;
- в аналитических витринах;
- в тестовых средах;
- при передаче данных между доменами.

### 3.4. Обезличивание

Применяется, когда восстановление личности пациента не требуется.

Используется для:

- BI-отчётности;
- обучения ML-моделей;
- разработки AI- и LLM-сервисов;
- статистических исследований;
- демонстрационных наборов данных.

Обезличивание должно исключать идентификацию пациента как по отдельным атрибутам, так и по их комбинации.

## 5. Защита на этапах жизненного цикла

| Этап | Основные меры |
|---|---|
| Сбор | Минимизация полей, проверка цели обработки, регистрация согласия |
| Передача | TLS/mTLS, аутентификация сервисов, минимизация состава данных |
| Обработка | RBAC/ABAC, проверка цели доступа, маскирование интерфейсов |
| Хранение | Шифрование, разделение доменов, резервное копирование |
| Использование в BI/ML/AI | Псевдонимизация или обезличивание, отдельная аналитическая зона |
| Выгрузка | Авторизация, обоснование выгрузки, маркировка, аудит и DLP |
| Архивирование | Шифрование, ограниченный доступ, фиксация срока хранения |
| Удаление | Контролируемое удаление из рабочих систем, кэшей и резервных копий |

## 6. Политики доступа

### 6.1. RBAC

Базовые роли:

| Роль | Разрешённые данные |
|---|---|
| Ресепшен | Контакты пациента, договор, расписание и статус записи |
| Медицинский специалист | Медицинская карта и анализы только связанных пациентов |
| Кассир | Сумма, услуга, статус оплаты и чек |
| Бухгалтер | Финансовые, кадровые и налоговые данные |
| Сотрудник склада | ТМЦ, оборудование и закупки |
| IT-администратор | Администрирование систем без штатного доступа к содержимому медицинских данных |
| Аналитик | Обезличенные или агрегированные данные |

### 6.2. ABAC

Для доступа к медицинским данным дополнительно проверяются атрибуты:

```text
employee.role
employee.branch_id
employee.specialization
patient.branch_id
appointment.doctor_id
record.patient_id
access.purpose
access.time
```

Пример правила:

```text
Врач может прочитать медицинскую карту,
если врач связан с пациентом через текущий или завершённый приём
и работает в соответствующем филиале.
```

## 7. Требования к журналированию

Для каждой операции необходимо фиксировать:

- идентификатор пользователя или сервиса;
- роль и атрибуты доступа;
- тип операции;
- категорию и идентификатор данных;
- дату и время;
- источник запроса;
- результат авторизации;
- основание и цель доступа.

Запрещено записывать в технические логи:

- полный текст медицинских заключений;
- паспортные данные;
- полные телефоны и email;
- содержимое лабораторных результатов;
- секреты, пароли и токены авторизации.

## 8. Управление ключами и секретами

Необходимо:

- хранить ключи отдельно от данных;
- использовать централизованную систему управления секретами;
- ограничить доступ сервисными ролями;
- выполнять ротацию ключей;
- журналировать операции с ключами;
- исключить ключи и пароли из исходного кода и конфигурационных файлов.

Возможные инструменты:

- HashiCorp Vault;
- Kubernetes Secrets совместно с внешним Secrets Manager;
- корпоративная KMS или HSM.

## 9. Защита аналитических данных

Для аналитической платформы необходимо создать отдельные зоны:

```text
Raw Zone
    |
    | очистка и классификация
    v
Protected Zone
    |
    | псевдонимизация / обезличивание
    v
Trusted Analytics Zone
```

В `Raw Zone` доступ разрешён только техническим процессам и ограниченной группе администраторов данных.

BI, ML и AI должны работать преимущественно с `Trusted Analytics Zone`.

## 10. Минимальные обязательные меры

Для всех потоков с уровнями `CONFIDENTIAL` и `RESTRICTED` обязательны:

1. Шифрование при передаче и хранении.
2. RBAC или ABAC с принципом минимальных привилегий.
3. Аудит чтения, изменения, выгрузки и удаления.
4. Маскирование чувствительных значений в интерфейсах и логах.
5. Установленный срок хранения и контролируемое удаление.

Для интеграций с внешними системами дополнительно обязательны:

- mTLS или OAuth 2.0;
- псевдонимизация идентификаторов;
- минимизация API-контрактов;
- запрет последовательного перебора идентификаторов;
- проверка принадлежности объекта пользователю;
- ограничение частоты запросов;
- мониторинг аномальной активности.

## 11. Вывод

Основными средствами защиты данных являются шифрование, строгая авторизация, аудит и управление жизненным циклом.

Маскирование применяется для отображения данных, псевдонимизация — для интеграций и контролируемой аналитики, обезличивание — для BI, ML и AI, где установление личности пациента не требуется.
