# Стратегия защиты данных: Encryption at Rest and In Transit

## 1. Цель

Документ определяет:

- какие данные компании «Медикаменте» необходимо защищать;
- как классифицировать данные по чувствительности, состоянию и профилю риска;
- какие механизмы использовать для защиты данных при хранении и передаче;
- какие средства автоматизированного контроля внедрить;
- какие программные и аппаратные средства включить в целевую архитектуру.

Стратегия распространяется на:

- клиентский портал и мобильное приложение;
- портал сотрудников;
- медицинскую информационную систему;
- CRM и реестр пациентов;
- платёжный сервис;
- интеграцию с лабораторией;
- 1С;
- файловые и объектные хранилища;
- резервные копии;
- аналитическую платформу;
- журналы аудита и мониторинга.

## 2. Классы данных

### 2.1. Уровни чувствительности

| Класс | Описание | Примеры |
|---|---|---|
| `PUBLIC` | Данные, разрешённые для открытого распространения | Адрес филиала, перечень услуг |
| `INTERNAL` | Внутренняя информация компании | Регламенты, внутренние справочники |
| `CONFIDENTIAL` | Персональные, договорные и финансовые данные | Ф. И. О., телефон, email, договор, чек |
| `RESTRICTED` | Медицинские, паспортные, зарплатные и иные критичные данные | Диагноз, анализы, медицинская карта, паспорт, зарплата |
| `SECRET` | Ключи, токены, пароли и иные секреты доступа | API keys, private keys, service credentials |

### 2.2. Состояния данных

| Состояние | Описание |
|---|---|
| `AT_REST` | Данные в БД, файлах, объектах, резервных копиях, логах и архивах |
| `IN_TRANSIT` | Данные при передаче по сети между пользователями, сервисами и внешними системами |
| `IN_USE` | Данные в памяти процесса, пользовательском интерфейсе и вычислительном контексте |
| `IN_BACKUP` | Резервные копии, snapshots, архивы и disaster recovery-копии |
| `IN_ANALYTICS` | Данные в озере данных, витринах, BI, ML и AI-средах |
| `IN_LOGS` | Технические, бизнес- и audit-события |

## 3. Классификация и меры защиты

| Данные | Чувствительность | Состояние | Профиль риска | Зачем защищать | Защита at rest | Защита in transit | Автоматизированный контроль |
|---|---|---|---|---|---|---|---|
| Ф. И. О., дата рождения | `CONFIDENTIAL` | БД, API, отчёты | Средний / высокий | Возможна идентификация пациента | TDE или шифрование диска; шифрование отдельных полей при необходимости | TLS 1.3, mTLS для service-to-service | DLP, классификатор PII, audit read/export |
| Телефон, email, адрес | `CONFIDENTIAL` | БД, уведомления, API | Высокий | Фишинг, спам, социальная инженерия | Field-level encryption; masked views | TLS 1.3; минимизация payload | Маскирование, DLP, запрет логирования полного значения |
| Паспортные данные | `RESTRICTED` | БД, документы, архив | Критический | Высокий ущерб при утечке и мошенничество | Field-level encryption; зашифрованное файловое хранилище; KMS/HSM | TLS 1.3, mTLS, подписанные документы | DLP, approval на экспорт, audit read/write/export |
| Медицинская карта | `RESTRICTED` | БД, документы, API | Критический | Медицинская тайна и риск дискриминации | TDE + field-level encryption; encrypted object storage; versioning | TLS 1.3, mTLS; ABAC до выдачи данных | SIEM, UEBA, массовое чтение, аномальные запросы |
| Диагнозы и анамнез | `RESTRICTED` | БД, аналитика | Критический | Наиболее чувствительные сведения о здоровье | Field-level encryption; псевдонимизация для аналитики | TLS 1.3, mTLS | Tagging, lineage, policy enforcement |
| Результаты анализов | `RESTRICTED` | БД, документы, интеграция | Критический | Медицинская тайна и риск подмены | Encryption at rest; checksum; versioning | mTLS + OAuth 2.0; signed response | Schema validation, signature verification, audit |
| Договоры и согласия | `CONFIDENTIAL` / `RESTRICTED` | Документы, архив | Высокий | Юридическая значимость и подписи | Encrypted object storage; versioning; retention | TLS 1.3; signed documents | Контроль срока хранения, integrity check |
| Записи на приём | `CONFIDENTIAL` | БД, API, уведомления | Средний | Раскрывают факт обращения и специалиста | TDE; минимизация хранимых данных | TLS 1.3 | Проверка ownership, rate limiting |
| Платёжные данные | `CONFIDENTIAL` | БД, интеграция, чек | Высокий | Финансовый ущерб и мошенничество | Encryption at rest; токенизация | TLS 1.3, mTLS, signed webhook | Fraud monitoring, idempotency, reconciliation |
| Карточные реквизиты | `RESTRICTED` | Только у провайдера | Критический | Высокий финансовый риск | Не хранить в системах компании | Передавать только через платёжного провайдера | Контроль отсутствия PAN/CVV в логах и БД |
| Кадровые данные | `RESTRICTED` | 1С, HR-система, документы | Критический | Паспортные, зарплатные и налоговые сведения | Field-level encryption; encrypted document storage | TLS 1.3, mTLS | Разделение ролей HR/Payroll, DLP, SIEM |
| Зарплата и банковские реквизиты | `RESTRICTED` | Payroll DB, банк | Критический | Финансовая конфиденциальность | Field-level encryption; HSM/KMS-backed keys | mTLS, signed request, idempotency | Audit corrections, anomaly detection |
| Данные поставщиков | `CONFIDENTIAL` | Складская система, 1С | Средний | Коммерческая и договорная информация | TDE; encrypted documents | TLS 1.3, mTLS | Audit changes and exports |
| Журналы аудита | `CONFIDENTIAL` | SIEM, archive | Высокий | Содержат идентификаторы и историю действий | Immutable/WORM storage; encryption at rest | mTLS; signed log shipping | Integrity monitoring, retention, alerting |
| Технические логи | `INTERNAL` / `CONFIDENTIAL` | Log storage | Средний / высокий | Возможна утечка PII, токенов и внутренних данных | Encryption at rest; restricted index access | TLS/mTLS | Secret scanning, PII redaction |
| Секреты и ключи | `SECRET` | Vault, KMS, HSM | Критический | Компрометация всей системы | Только Vault/KMS/HSM; envelope encryption | mTLS; short-lived credentials | Rotation, access audit, secret scanning |
| Резервные копии | По максимальному классу данных | Backup storage | Критический | Содержат полный объём данных | Separate encryption key; encrypted backup; immutable copy | TLS/mTLS при передаче | Backup audit, restore tests, key rotation |
| Аналитические наборы | `CONFIDENTIAL` / `RESTRICTED` | Data Lake | Высокий | Риск повторной идентификации | Zone-based encryption; pseudonymization/anonymization | mTLS между ingestion-компонентами | Data lineage, quality gates, policy checks |
| Тестовые данные | Не выше `INTERNAL` | Test environment | Высокий при копировании production | Риск утечки через non-prod | Только synthetic/anonymized datasets | TLS | CI/CD gate, запрет production dumps |

## 4. Защита данных при хранении

### 4.1. Базы данных

Для PostgreSQL, CRM, медицинской системы и платёжного сервиса:

- шифрование дисков или томов;
- Transparent Data Encryption, если поддерживается выбранной платформой;
- шифрование отдельных полей для `RESTRICTED`-данных;
- отдельные ключи для разных доменов;
- шифрование snapshots и резервных копий;
- запрет хранения секретов в БД в открытом виде;
- ограничение доступа по сервисным ролям;
- аудит чтения, изменения и выгрузки.

Рекомендуемый подход:

```text
Data Encryption Key
    ↓ encrypted by
Key Encryption Key in KMS/HSM
```

Это позволяет ротировать мастер-ключи без полного перешифрования всех данных.

### 4.2. Файлы и объектное хранилище

Для PDF, JPG, договоров, заключений и результатов анализов:

- server-side encryption с ключами KMS;
- отдельный bucket или namespace для каждого класса данных;
- object versioning;
- checksum;
- запрет публичного доступа;
- короткоживущие pre-signed URL;
- retention и lifecycle policy;
- WORM/immutable режим для audit-данных;
- резервирование в отдельный защищённый контур.

### 4.3. Рабочие станции и серверы

Необходимо:

- BitLocker или LUKS для полнодискового шифрования;
- TPM 2.0 для безопасного хранения ключевого материала;
- запрет локального хранения медицинских файлов;
- MDM/EDR-контроль рабочих станций;
- автоматическая блокировка экрана;
- запрет подключения неавторизованных USB-носителей;
- централизованное удаление данных при компрометации устройства.

### 4.4. Резервные копии

Требования:

- отдельный ключ шифрования;
- физическое или логическое отделение от production;
- immutable backup;
- доступ только backup-service account;
- журналирование операций;
- регулярный restore test;
- запрет хранения ключей рядом с резервной копией;
- контролируемое уничтожение просроченных копий.

## 5. Защита данных при передаче

### 5.1. Пользовательские соединения

Для порталов и мобильного приложения:

- TLS 1.3;
- HSTS;
- безопасные cipher suites;
- OAuth 2.0 / OpenID Connect;
- MFA;
- короткоживущие access tokens;
- проверка ownership каждого ресурса;
- rate limiting;
- защита от IDOR;
- запрет передачи чувствительных данных в URL.

### 5.2. Межсервисное взаимодействие

Для service-to-service:

- mTLS;
- service identity;
- короткоживущие сертификаты;
- авторизация каждого запроса;
- schema validation;
- idempotency-key;
- replay protection;
- correlation id без включения PII;
- централизованная ротация сертификатов.

### 5.3. Внешние интеграции

#### Лаборатория

- mTLS;
- OAuth 2.0 Client Credentials;
- псевдонимизированный `lab_subject_id`;
- минимальный контракт;
- цифровая подпись ответа;
- allow-list API;
- rate limiting;
- аудит запросов и результатов.

#### Платёжный провайдер

- отсутствие хранения PAN/CVV;
- tokenization;
- TLS 1.3;
- mTLS или подписанный webhook;
- replay protection;
- idempotency;
- reconciliation.

#### 1С, банк, ФНС и СФР

- изолированный integration-service;
- mTLS;
- service account;
- подписанные документы;
- ограниченный набор операций;
- запрет прямого доступа пользователей к интеграционным каналам;
- аудит экспортов и корректировок.

### 5.4. Kafka и асинхронные потоки

Для Kafka:

- TLS для broker/client;
- SASL-аутентификация;
- ACL для topic;
- отдельные topics по доменам;
- запрет передачи лишних PII;
- schema registry;
- шифрование чувствительных полей payload;
- audit producer/consumer access;
- короткий retention для временных событий;
- dead-letter topic с тем же уровнем защиты.

## 6. Защита данных при использовании

Шифрование at rest и in transit не защищает данные после расшифрования.

Дополнительно необходимы:

- RBAC и ABAC;
- маскирование полей в UI;
- запрет отображения полного паспорта, телефона и банковских реквизитов без необходимости;
- ограничение clipboard и export;
- session timeout;
- запрет общих учётных записей;
- controlled break-glass access;
- журналирование факта расшифрования чувствительных полей;
- запрет PII в exception и application logs.

---

## 7. Управление ключами

### 7.1. Основные правила

- ключи не хранятся в исходном коде;
- ключи не хранятся в Git, Helm values и Docker image;
- используется централизованный KMS/Vault;
- ключи разделяются по средам и доменам;
- применяются short-lived credentials;
- включается автоматическая ротация;
- доступ к ключам фиксируется в audit log;
- backup-ключи отделяются от production-ключей;
- критичные мастер-ключи хранятся в HSM.

### 7.2. Иерархия ключей

```text
Root Key / Master Key
        ↓
Domain Key
        ↓
Data Encryption Key
        ↓
Encrypted data
```

Рекомендуется использовать отдельные domain keys для:

- медицинских данных;
- CRM;
- платежей;
- HR и зарплаты;
- аналитической платформы;
- резервных копий;
- журналов аудита.

### 7.3. Ротация

| Тип | Рекомендация |
|---|---|
| TLS-сертификаты | Автоматическая ротация, короткий срок действия |
| Service credentials | Короткоживущие токены |
| Data Encryption Keys | Регулярная ротация по политике |
| Master keys | Плановая ротация с dual-key period |
| Backup keys | Отдельная политика и проверка восстановления |
| Emergency rotation | Немедленно при подозрении на компрометацию |

## 8. Автоматизированный контроль

### 8.1. Контроль классификации

Необходимо автоматически проверять:

- наличие classification tags;
- наличие owner;
- наличие retention policy;
- наличие `PURPOSE`;
- отсутствие `RESTRICTED`-данных в публичных API;
- отсутствие production PII в тестовых средах.

Инструменты:

- OpenMetadata;
- DataHub;
- Apache Atlas;
- собственные CI/CD-проверки схем и контрактов.

### 8.2. Контроль исходного кода и CI/CD

Pipeline должен блокировать релиз при обнаружении:

- секретов в репозитории;
- приватных ключей;
- PII в тестовых fixtures;
- незашифрованных connection strings;
- отсутствия TLS;
- отсутствия тегов у чувствительных полей;
- логирования токенов и медицинских данных;
- незащищённых S3 buckets;
- отсутствия encryption settings в Terraform/Helm.

Инструменты:

- Gitleaks;
- TruffleHog;
- Semgrep;
- SonarQube;
- Checkov;
- Trivy;
- OPA / Conftest.

### 8.3. Контроль runtime

Необходимо отслеживать:

- массовое чтение медицинских записей;
- частые отказы авторизации;
- выгрузки большого объёма данных;
- доступ из нетипичного филиала;
- использование break-glass роли;
- обращения к данным вне рабочего времени;
- неожиданные decrypt-операции;
- аномальный трафик к лаборатории и 1С;
- изменения ключей и политик;
- ошибки проверки подписи.

Инструменты:

- SIEM;
- VictoriaMetrics / Prometheus;
- Grafana;
- OpenSearch / Elasticsearch;
- Falco;
- Wazuh;
- UEBA-механизмы.

### 8.4. Контроль DLP

DLP должна проверять:

- email-вложения;
- выгрузки CSV/XLSX;
- копирование на USB;
- массовое скачивание документов;
- отправку ПДн в мессенджеры;
- публикацию данных в неконтролируемые облака;
- печать конфиденциальных документов.

## 11. Минимальный обязательный baseline

Для `CONFIDENTIAL` и `RESTRICTED` данных обязательны:

1. TLS 1.3 при передаче.
2. mTLS для межсервисных и внешних интеграций.
3. Шифрование at rest.
4. KMS/Vault для ключей и секретов.
5. RBAC/ABAC.
6. Audit read/write/export/delete.
7. Маскирование в UI и логах.
8. Retention policy.
9. Encrypted backup.
10. Автоматическая проверка конфигураций.

Для `SECRET` данных обязательны:

1. Хранение только в Vault/KMS/HSM.
2. Short-lived credentials.
3. Ротация.
4. Запрет логирования.
5. Отдельный audit.
6. Emergency rotation procedure.

---

## 12. Критерии готовности

Решение считается готовым, если:

- 100% `CONFIDENTIAL` и `RESTRICTED` объектов классифицированы;
- для каждого объекта определён владелец;
- для каждого потока определены at rest и in transit меры;
- все внешние интеграции используют TLS/mTLS;
- секреты отсутствуют в Git и image;
- production PII не используется в test;
- резервные копии зашифрованы и проходят restore test;
- decrypt и export операции журналируются;
- CI/CD блокирует небезопасные конфигурации;
- SIEM получает события всех критичных систем.

---

## 13. Вывод

Защита данных должна строиться как сквозной механизм.

Шифрование при хранении защищает БД, файлы, документы, логи и резервные копии. Шифрование при передаче защищает пользовательские, межсервисные и внешние потоки. Однако оба механизма эффективны только совместно с управлением ключами, RBAC/ABAC, тегированием, аудитом, DLP, Data Lineage и автоматизированным контролем.
